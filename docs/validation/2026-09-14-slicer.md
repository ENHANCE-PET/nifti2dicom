# Installed Slicer acceptance — 2026-09-14

The receiver defects documented below were subsequently fixed in an optional
external integration. See the [repair acceptance](2026-09-14-slicer-fix.md) for
normal installed-import results. This baseline report and its failure evidence
are retained; the original stock-reader behavior has not been rewritten.

## Baseline outcome: automatic 4D acceptance is blocked

The installed **Slicer 5.12.0**, revision **a5df714**, successfully loaded static
PET and binary/multilabel SEG through its normal DICOM plugins. Its automatic
loading paths failed the two dynamic PET cases. Successful diagnostic controls
do **not** override those failures or establish general Slicer compatibility.

No converter behavior, installed Slicer source, original imaging data or user
DICOM database was changed. Sessions used `--testing`, fresh temporary databases
and the installed readers. The package source digest is unchanged from the
[PET precision audit](2026-09-14-pet-precision.md).

| Case | Installed receiving path | Observed result |
| --- | --- | --- |
| Static RIDER PET, 47 images | Default scalar-volume reader | Exact agreement with exported quantitative values; physical-coordinate checks pass |
| Binary SEG, one segment | Default SEG plugin and bundled dcmqi | Zero mask differences; all 47 source references retained |
| Multilabel SEG, three segments | Default SEG plugin and bundled dcmqi | Zero mask differences; all 47 source references retained |
| Dynamic RIDER PET, 32 × 47 images | Default MultiVolume reader | **Fails quantitative checks:** later floating-point frames are cast into first-frame integer storage |
| Dynamic FLT PET, 45 × 35 images | Default selection offers one scalar stack | **Fails temporal grouping:** timepoints are treated as spatial slices; geometry warning and an inappropriate regularization transform result |

Measurements, per-timepoint checks, failures, selected loadables and artifact
hashes are in the [machine-readable report](2026-09-14-slicer.json).

## What was checked

The three public series are the unchanged GE classic-PET outputs from the
precision audit: RIDER static, RIDER dynamic and ACRIN FLT dynamic, all in BQML.
All **3,126 output-file hashes** were compared with their prior successful
DICOM 2026c validator reports. No IOD validator was rerun in this viewer pass;
in particular, this is not a new `dciodvfy` result.

Expected real-valued arrays and affines were reconstructed independently from
the original public DICOM. Each loaded Slicer voxel was mapped from IJK through
RAS/LPS physical coordinates into that original grid. Coverage had to be
one-to-one. The audit also matched loaded planes to referenced SOP instances,
decoded the exported pixel/rescale values independently, and checked each
plane's quantization bound against the original values.

Dynamic checks compare actual frame content, referenced frame times and frame
durations. For sequence controls, every browser index was selected and the
displayed proxy's values and affine compared with its sequence data node.
These are numerical and geometric checks, not just visual inspection.
The final browser checks use a checksum, affine copy and SOP-instance UID string
saved **before** navigation. Comparing two live arrays would be insufficient:
Slicer's shallow-copy/SaveChanges path can share buffers. Review identified this
oracle gap; a shared-buffer flip reproduced it, and both dynamic controls were
rerun with immutable expectations.

The normal selection test uses the installed
`DICOMUtils.selectHighestConfidenceLoadables` and
`DICOMLoadableTable.setLoadables` together. The latter resolves duplicate
interpretations as the GUI does. The FLT selected loadable has a warning: the
GUI would ask whether to proceed. This audit proceeded to characterize that
interpretation; it is **not** reporting a warning-free FLT import.

## Dynamic failures and diagnostic controls

### RIDER: first-frame dtype contaminates later frames

The first two decoded temporal volumes are zero-valued `uint16`; subsequent
volumes require `float64` after their rescale mappings. The installed
`MultiVolumeImporterPlugin.load` allocates the entire MultiVolume using the
first volume's scalar type. Assigning later floating-point volumes into that
array truncates fractions and wraps out-of-range values.

The default loaded MultiVolume is `uint16`. Its maximum disagreement with the
exported quantitative values is **3,604,480.087999998 BQML**. Across the scan,
**1,607,539 voxels** exceed their original-source quantization bounds. Frame
reference ordering and physical locations still pass: this is a quantitative
storage failure, not an observed spatial/time reversal.
An additional pydicom-only reproduction decoded all exported frames and cast
them to `uint16`: it reproduced all 32 loaded MultiVolume checksums and every
recorded error. Without that cast, independently decoded frame checksums match
all 32 accurately loaded sequence frames.

The installation also has a plugin-dispatch incompatibility.
`DICOMPlugin.examineForImport` now calls `examineFiles` directly. Because that
returns a RIDER loadable, `DICOMUtils` does not invoke the MultiVolume plugin's
legacy `examine` override, where sequence alternatives are constructed.
The Sequences module is installed and loaded; its absence is not the cause.

As a **non-default diagnostic control**, calling the installed plugin's legacy
`examine` method and choosing its volume-sequence interpretation preserves
every value in all **32 frames / 24,641,536 voxels** exactly relative to exported
DICOM. All 32 browser proxies and original frame times/durations pass.
This does not mean the ordinary import workflow has been fixed.

That native sequence interpretation uses indices `0` through `31`, with no
index unit. Acquisition-time labels survive in `MultiVolume.FrameLabels`,
but a browser index must not be interpreted as elapsed seconds or PET duration.

### FLT: native PET timing is not recognized

The exported FLT series has 45 distinct `FrameReferenceTime` values and
`NumberOfTimeSlices=45`, while AcquisitionTime, SeriesTime and ContentTime are
constant across the series. The installed MultiVolume strategies do not
recognize FrameReferenceTime. Their InstanceNumber fallback requires an MR
RepetitionTime, which this PET series does not provide. Calling legacy
`examine` does not offer a sequence for this case either.

The automatic selection therefore offers a 1,575-image scalar stack, warns
about repeated slice positions, and attempts spatial regularization if loaded.
This is not an acceptable interpretation of a 45-timepoint scan.

A second **non-default diagnostic control** explicitly groups this known
classic-PET fixture by FrameReferenceTime, loads each 35-plane group through
Slicer's native scalar reader, and assembles a sequence indexed in milliseconds.
All **45 frames / 25,804,800 voxels** agree exactly with exported DICOM, with
correct original frame times/durations and all 45 browser proxies checked.
This fixture-specific control is not a shipped importer or a general timing
inference policy.

Together with static PET, the accurate read paths cover **51,216,384 voxels**
with zero additional intensity error from Slicer. Loaded world-coordinate
residuals are below 0.000001 mm in these cases. Original-to-export quantization
error remains as measured previously; zero *viewer-added* error is not lossless
conversion of arbitrary original floats. No spatial or temporal reversal was
detected in these successful paths. Automatic 4D acceptance remains blocked.

## SEG and presentation

The SEG fixtures are explicitly synthetic geometric QA masks, not anatomical
predictions or a fresh LION/MOOSE run. They use the exported static PET as their
reference. Their asymmetric shapes make spatial errors measurable.

- Binary: label 1, 3,267 foreground voxels; zero differences after Slicer import.
- Multilabel: original IDs 5, 300 and 1024 map to three DICOM segments, containing
  3,267, 864 and 480 voxels; zero differences for every segment.
- Segment names and the complete set of 47 source-image references survive.

Slicer's normal SEG plugin invoked its bundled `segimage2itkimage`, reporting
dcmqi repository tag **v1.5.4**, revision **a102298**. Comparison used the masks
actually loaded into Slicer, extracted onto the loaded reference volume grid.

Native four-up screenshots were inspected. Sequence display contrast can remain
fixed to an early frame; RIDER's initially zero frame produces a saturated
later-frame view despite correct sequence voxels. Original screenshots are
retained alongside separately named `-windowed.png` presentation controls.
Those controls change only display window/level, using the positive-voxel 99th
percentile for geometric inspection. They are not clinical display presets and
must not be mistaken for default-import screenshots. Original and adjusted
display settings are recorded in JSON.

## Reproduction and limits

Raw scripts, independent truth arrays, logs, generated SEG and screenshots are
under `/private/tmp/nifti2dicom-slicer-acceptance.RgtW20`. This is temporary local
storage, not durable public fixture hosting. The JSON records the script and
installed-plugin hashes so results are tied to this installation, not every
Slicer version.

Run `accept_slicer.py` inside Slicer with `--testing --no-splash --python-script`.
`SLICER_QA_CASE` selects a case from `cases.json`; `SLICER_QA_RUN` must be a fresh
artifact/database prefix. Leave `SLICER_QA_MODE` unset for default selection.
The explicitly named modes `legacy_examine_sequence` and
`explicit_frame_time_sequence` are diagnostic controls only. The script must
execute directly: deferring it to a zero-delay timer under testing mode caused
the first probes to run during module teardown. That harness problem was
corrected before the reported runs; it is not a converter/Slicer import defect.

Slicer logs attempts to parse the non-DICOM `conversion.json` sidecar during
folder indexing; it still indexes the DICOM files. Those log messages are
separate from the actual dynamic failures. Two empty probe-created database
files were moved out of the repository into the temporary QA directory.

The unchanged package passes **730 regression tests** in this pass. No release,
push, new model inference, private-data transfer or Slicer installation patch
was performed. These results do not establish clinical readiness, other-vendor
PET support, genuine 4D MR/CT acceptance, or intended PACS compatibility.

The next acceptance work is receiver-side: resolve dispatch/dtype handling,
provide a tested PET-native temporal interpretation, and rerun these same
positive and negative cases. A supported default import must preserve values,
geometry and time together before this viewer gate can be closed.
